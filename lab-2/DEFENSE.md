# DEFENSE - Завдання 2: Вимоги та Use Cases

**Намір і критерії (1-2 речення):**
Мета - сформулювати EARS-вимоги, User Stories, Gherkin-сценарії, Use Case діаграму та матрицю трасування для системи бронювання квитків у кінотеатр.
Основні критерії приймання: повна узгодженість із моделлю даних Лаб 1, обробка 10-хвилинного таймауту через статуси в ORDER, а також наявність непокритої вимоги для матриці N:M.

**Топ-3 розбіжності (між специфікацією та артефактом) + коміт-виправлення:**
- Неіснуючі поля та сутності: AI намагався додати неіснуючу таблицю SCREENING та поле Status у таблицю SEAT - Виправлено перенесенням логіки бронювання в таблицю ORDER із таймаутом та статусами Pending, Paid, Cancelled (Коміт: Виправлення Помилки 1 - логіка таймауту та статусів замовлення без поля status у SEAT)
- Відсутність спеціальних умов та непокритих вимог: AI згенерував стандартні вимоги без урахування знижок та повним 100% покриттям - Виправлено додаванням умови для VIP-клієнтів та винесенням вимоги про 3D-окуляри як непокритої (Коміт: Виправлення Помилки 2 - фіксація VIP-знижки та непокритої вимоги для 3D-фільмів)
- Помилкові зв'язки в Use Case: AI зв'язав скасування замовлення через include, ніби воно відбувається завжди - Виправлено зміною на extend з умовою таймауту або відмови платіжного шлюзу (Коміт: Виправлення Помилки 3 - побудова Use Case діаграми та матриці трасування N:M)

**Ключове рішення - які альтернативи зважив і чому обрав цю (ADR):**
Розбиття процесу купівлі на окремі Use Cases (вибір місця, створення замовлення, оплата) замість одного монолітного сценарію
Альтернативи (монолітний сценарій) ускладнюють обробку помилок і не дозволяють чітко показати роботу із зовнішнім платіжним шлюзом та таймаутами
Обрано декомпозицію через зв'язки include та extend, оскільки це ізолює бізнес-логіку та відповідає структурі бази даних з Лаб 1

**Перевірка - узгодженість із попередньою моделлю (як перевірив):**
Перевірка здійснювалася на узгодженість між вимогами (spec.md), Use Case діаграмою та фінальною структурою БД
Я перевірив кожен сценарій і зв'язок на відповідність таблицям CLIENT, HALL, SEAT, MOVIE, ORDER, PAYMENT без додавання зайвих сутностей

(Атрибути та сутності з першої та другої лаби відрізняються, бо я перероблював діаграму для першої лаби по базам даних та вирішив робити такі ж самі атрибути та зв'язки як у ній)
