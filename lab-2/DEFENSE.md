**Намір і критерії (1-2 речення):**
Мета — сформулювати EARS-вимоги, User Stories, Gherkin-сценарії, Use Case діаграму та матрицю трасування для системи бронювання квитків у кінотеатр.
Основні критерії приймання: повна узгодженість із моделлю даних Лаб 1, обробка 10-хвилинного таймауту через статуси в ORDER, прибрання внутрішніх дій системи з Use Case діаграми та наявність непокритої вимоги для матриці N:M.

**Топ-3 розбіжності (між специфікацією та артефактом) + коміт-виправлення:**
- **Неіснуючі поля та внутрішні дії системи у Use Case:** AI намагався додати внутрішні дії системи (скасування за таймаутом, застосування знижки) як окремі прецеденти. — Виправлено: вилучено дії системи з діаграми, перенесено логіку в сценарії, додано узагальнення акторів `Guest <|-- Client`. (Коміт: *оновив Use Case діаграму: виправив синтаксис та структуру*)
- **Відсутність спеціальних умов та непокритих вимог:** AI згенерував стандартні вимоги без урахування знижок та з повним 100% покриттям. — Виправлено додаванням умови для VIP-клієнтів та винесенням вимоги про 3D-окуляри як непокритої. (Коміт: *Виправлення Помилки 2 - фіксація VIP-знижки та непокритої вимоги для 3D-фільмів*)
- **Помилкові зв'язки в Use Case:** AI зв'язав скасування замовлення через `include`, ніби воно відбувається завжди. — Виправлено зміною на `extend` з умовою таймауту або відмови платіжного шлюзу. (Коміт: *Виправлення Помилки 3 - побудова Use Case діаграми та матриці трасування N:M*)

**Ключове рішення - які альтернативи зважив і чому обрав цю (ADR):**
Розбиття процесу купівлі на окремі Use Cases (вибір місця, створення замовлення, оплата) замість одного монолітного сценарію.
Альтернативи (монолітний сценарій) ускладнюють обробку помилок і не дозволяють чітко показати роботу із зовнішнім платіжним шлюзом та таймаутами.
Обрано декомпозицію через зв'язки `include` та `extend`, оскільки це ізолює бізнес-логіку та відповідає структурі бази даних з Лаб 1.

**Перевірка - узгодженість із попередньою моделлю (як перевірив):**
Перевірка здійснювалася на узгодженість між вимогами (`spec.md`), Use Case діаграмою та фінальною структурою БД.
Я перевірив кожен сценарій і зв'язок на відповідність таблицям `CLIENT`, `HALL`, `SEAT`, `MOVIE`, `ORDER`, `PAYMENT` без додавання зайвих сутностей (атрибути та сутності повністю відповідають оновленій ER-моделі з Лаб 1).
