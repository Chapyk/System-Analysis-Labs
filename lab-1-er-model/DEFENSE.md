# DEFENSE - Завдання 1: Домен і модель даних (ER)

**Намір і критерії (1-2 речення):**
Мета - створити декларативну ER-модель для системи бронювання квитків у кінотеатр
Основні критерії приймання: нормалізація бази даних до 3NF, типізація всіх ідентифікаторів як string, логічне відображення зв'язків багато-до-багатьох (без фізичних сполучних таблиць)

**Топ-3 розбіжності (між специфікацією та артефактом) + коміт-виправлення:**
- Типізація ключів: AI спочатку змішав типи string та int для ID різних сутностей - Виправлено додаванням вимоги про UUID у специфікацію (Коміт: Виправлення Помилки 1 - вимагати використання рядкових UUID для всіх первинних і зовнішніх ключів)
- Порушення нормалізації (3NF): AI міг помістити атрибут price безпосередньо у сутність TICKET - Виправлено жорсткою фіксацією правила, що ціна залежить від сеансу (Коміт: Виправлення Помилки 2 - фіксація правила 3NF для атрибута price)
- Зайва фізична таблиця: AI часто генерує проміжні таблиці для зв'язків багато-до-багатьох - Виправлено прямою забороною генерувати сполучні таблиці (Коміт: Виправлення Помилки 3 - заборона сполучних таблиць для зв'язку багато-до-багатьох)

**Ключове рішення - які альтернативи зважив і чому обрав цю (ADR):**
Використання асоціативної сутності TICKET замість простого зв'язку M:N між USER та SCREENING
Альтернативи (чистий зв'язок або масив у юзера) не дозволяють зберігати атрибути місця або порушують першу нормальну форму
Обрано асоціативну сутність, оскільки квиток має власні критичні атрибути (деталі в adr/001-ticket-associative-entity.md)

**Перевірка - узгодженість із попередньою моделлю (як перевірив):**
Перевірка здійснювалася на узгодженість між вимогами (spec.md) та фінальним артефактом (diagram.md)
Я перевірив згенерований код Mermaid: кардинальності та наявність зовнішніх ключів строго відповідають текстовому опису бізнес-логіки, сутності не містять транзитивних залежностей
